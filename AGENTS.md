## General Principles

- **Minimize comments**: Code should be self-documenting through clear naming and structure
- **Only comment when necessary**: Add comments only when they provide valuable context that isn't obvious from the code itself
- **English only**: All comments must be written in English
- **Lifecycle logging vocabulary**: use `phase`, `step`, `outcome`, `service_name`, `install_dir`, `scope`, `init_system`, `version`, `watchdog_version`, and `error` consistently. INFO narrates lifecycle decisions and outcomes, DEBUG is repeatable detail, WARN is degraded but continuing, and ERROR requires human action or stops safe progress
- **End-to-end journeys**: tests under `test/integration` copy prebuilt binaries from `DAEMONPILOT_TEST_FIXTURES`, or build fixtures with `go build` into `t.TempDir()` when that directory is unset, exercise real processes and files, synchronize by observable conditions with bounded deadlines, and skip with a reason only when the host genuinely cannot provide the required facility. Run them with `go test -count=3 ./test/...` in the configured Go workspace; add a journey by extending a fixture's environment-driven behavior and asserting the externally visible process/file result

## Project Structure

- `pkg/httpsource/` - Streaming HTTP update source with manifest polling, authentication, and signature headers
- `pkg/release/` - Streaming digest signing and cached HTTP release handler
- `cmd/daemonpilot-sign/` - Release signer CLI; private keys are hex-encoded 32-byte ed25519 seeds
- `internal/updatehttp/` - Shared HTTP signature/hash header defaults and validation
- `pkg/daemonpilot/` - Public API: types, config, CLI routing, command handlers
- `internal/daemon/` - Init-system service managers (systemd, launchd, OpenRC, dinit, Finit, sysvinit, runit, s6, procd, BusyBox init, crontab)
- `internal/ipc/` - IPC between watchdog and worker processes over inherited anonymous pipes, passed to the child via `exec.Cmd.ExtraFiles` and located by the `DAEMONPILOT_IPC_FD` environment variable (not a Unix domain socket)
- Watchdog log collection: `Config.CollectWatchdogLogs` opts into a byte-capped memory ring owned by `Watchdog`, never by the per-worker `ipc.Server`. Workers pull with `CollectWatchdogLogs(finishedThrough)`; returning a batch does not acknowledge it, and only a later cursor removes lines through that sequence. Keep the transport pull-only and disk-free so logging cannot make the supervisor depend on worker health or flash-backed storage
- Installed binary paths: every updater and watchdog live, staged, rollback, quarantine, and cleanup path derives from `daemonpilot.InstalledBinaryName`; Windows requires `<name>.exe`, while the raw service name remains the key for state files and rollback digests. The normalization is idempotent, so apply it at boundaries instead of rebuilding binary paths from `Config.Name`
- `internal/watchdog/` - Watchdog loop, backoff, shutdown logic
- `internal/updater/` - Self-update: download, verify, selftest, apply, rollback
- `internal/crypto/` - Ed25519 signature verification
- `internal/process/` - Application signal handling and Windows service integration
- Process supervision mechanics live in procguard (`github.com/ovineko/procguard`): backoff, child process groups/trees, graceful stop and escalation, parent-death monitoring, and limits. The watchdog supplies launch specs and interprets state/outcomes; lossy events are for logging only.
- Probation checks `Supervisor.State().Running` together with `StartedAt`: the leader can have crashed while its descendants are still being cleaned up. A retained PID or an unfinished launch does not prove worker liveness.
- Re-executing the binary: every path that runs this binary again — the service manifest (`buildServiceConfig`), the worker spawn, the exec-through child, and the updater's `selftest`/`watchdog-version` probes — builds its arguments with `daemonpilot.DaemonpilotArgs(cfg.CommandPrefix, verb...)`. A new path that hardcodes the verb works until a consumer sets `Config.CommandPrefix`, and then starts the wrong program. The updater receives the prefix through the optional `SetCommandPrefix` capability rather than through the registered factory signature
- `pkg/daemonpilot/metrics/` - Optional Prometheus collectors. It is a separate package so that `pkg/daemonpilot` does not import the Prometheus client: an application that exports no metrics would otherwise carry it and its protobuf dependency, about nine megabytes of binary. Nothing in `pkg/daemonpilot` may import it back
- Staged probation belongs to the supervising watchdog, including an exec-through child. On successful child rollback, stop the entire run and return nil (exit 0), so the proxy resets backoff and immediately launches the restored disk image. The proxy waits for child exit and only restores on repeated child crashes/start failures; it must never commit based on child uptime. Keep update checks gated until rollback and shutdown finish. Verified restore consumes the copy and digest; quarantine moves invalid copies aside before another owner can act.
- `pkg/daemonpilot/setup/` - Factory registration: wires internal implementations (watchdog, updater) to the public API via blank import
- `test/integration/` - Cross-package integration tests
- `examples/` - Example projects
- `docs/` - Documentation site source (Zensical), published to <https://daemonpilot.ovineko.com/>
- `docs/.plans/` - Internal implementation plans; the leading dot keeps them out of the published site

## Build & Test

- Real-init first-run pitfalls: systemd uses `--cgroupns=host` with the writable host cgroup bind (broader than other profiles), and console logging plus a container TTY captures early boot failures. Finit is ready only at runlevel 2. Alpine package-index fetch errors need bounded retries, never a missing-package skip. Keep manifest `.backup` separate from binary `.restore` in cleanup contracts.
- Real-init second-run pitfalls: OpenRC supervisor availability uses executable lookup, not `supervise-daemon --help`, which requires `RC_SVCNAME` before parsing options. Runit stop must wait for down state (`sv -w 30 stop`); `sv down` only signals and races uninstall lock cleanup. Systemd config-rejection fixtures use duplicate `ExecStart` directives under `Type=simple`; a nonexistent bare command is valid syntax and can fail after start reports success.
- SysVinit/BusyBox background supervision must run in a redirected subshell `(supervise) </dev/null >/dev/null 2>&1 &`: redirecting the function alone leaves shell-saved output descriptors open and hangs CombinedOutput. Test generated scripts through captured pipes. runit/s6 Start retries only missing-supervisor registration races with a bounded deadline.
- Dinit env files contain literal `NAME=VALUE` records, not Go/shell-quoted values. Finit sources a POSIX shell fragment through its fixed wrapper rather than using an `env:` directive. Both reload changed definitions after environment writes and before Start; restore paths must schedule a reload too. Dinit uninstall uses persistent disable then unload. procd status must read JSON instance booleans, not search for the substring `running`.
- Real init Docker contracts: `task e2e:docker:init` runs `TestInitProfiles`; G1 stays on `e2e:docker`. Images live in `e2e/docker/images/<init>/Dockerfile`, with tagged bases and Dockerfile-SHA256 image tags. Root-owned production state is read through the fixture inside the container. Reboots must use `docker restart` and fresh timestamps, since namespace PIDs can repeat. Staged updates under restart-capable Unix init currently direct-exec with the same PID; SIGKILL independently tests init recovery. Never claim staged exit-for-init behavior.
- Crontab commands must export environment assignments before `cd`; assignments attached only to `cd` do not reach the service. Manual start keeps the log redirect and detaches all standard descriptors so CombinedOutput cannot wait on the long-lived service.
- Docker contracts: `task e2e:docker` (requires Docker); native companion: `GOWORK=off go test -tags e2e_docker -count=1 -v -run TestNative ./e2e/docker`. A contract change needs a scenario + negative control in `e2e/docker/scenarios_test.go` (G1) or `e2e/docker/init_scenarios_test.go` (G2), and `docs/guides/testing.md`. The native companion uses the real HTTP release handler through an in-memory transport when sockets are unavailable; it does not prove PID namespace behavior.
- The Docker fixture uses `GO_DAEMONPILOT_E2E_CONFIG` for its inherited config path: a `DAEMONPILOT_`-prefixed fixture variable would be stripped by the worker launch environment filter. All builds and bind volumes live in test temporary directories.

- `go.mod` pins the published `github.com/ovineko/procguard` module, verified by `go.sum`. No sibling checkout, local replacement, or CI revision override is required. Use `GOWORK=off` for isolated verification against the pinned dependencies.
- Ignore the root binary as `/daemonpilot`, never an unanchored `daemonpilot` pattern, which also excludes `pkg/daemonpilot` and its setup, metrics, tests, and fuzz corpora from Git.

- Run all tests: `go test ./...`
- Run with race detector: `go test -race ./...`
- Toolchain: `@shibanet0/datamitsu-config` 0.5.0. After changing managed configuration, run `pnpm dm init`; rewrite project-owned configs only with explicit `pnpm dm config reconcile`. Keep tool exclusions and their reasons in the root `.datamitsuignore`.
- Quality gate: `pnpm dm check --fail-fast=false` locally; CI runs `pnpm dm lint --fail-fast=false` so verification cannot rewrite files. HTTP manifest polling represents availability explicitly internally and adapts it to the public `(nil, nil)` no-update contract.
- The pinned golangci-lint analyzer cannot read Go 1.27.2 export data and is disabled in `.datamitsuignore`. Keep `go build` and `go vet` in local and hosted verification; do not disable them to match an analyzer failure.
- CI (`.github/workflows/ci.yml`) runs build, vet, unit/integration, and race tests on Linux amd64/arm64, macOS 15 Intel/arm64, and Windows 2025 amd64 plus Windows 11 arm64 (race on amd64). It runs native SCM/launchd E2E on Windows/macOS. `.github/workflows/e2e.yml` runs Linux Docker lifecycle and real-init contracts on dispatch and weekly schedule; `.github/workflows/platform-e2e.yml` runs five Linux architectures and BSD guest tests (FreeBSD/OpenBSD/NetBSD amd64/arm64, DragonFly amd64) on dispatch and weekly schedule. Cross-builds do not establish runtime behavior. Pin third-party actions to a commit SHA
- Build the docs site: `pnpm dm exec task -- docs:build`; preview it with `docs:serve`
- Zensical has no `exclude_docs` support: everything under `docs/` is published except dot-directories. Internal notes go in `docs/.plans/` — a plan written to `docs/plans/` (as the ralphex skill does) would go live, so move it

## Conventions

- HTTP releases: signatures cover the optional `SignatureContext` bytes followed by the SHA-256 digest, never the full binary. Empty context preserves legacy signatures; `internal/crypto.DigestMessage` constructs the message for both signer and verifier. Use a purpose/version context ending in NUL (e.g. `"myapp-binary-v1\x00"`); `VerifyFunc` bypasses the built-in check and ignores the context. Header defaults belong to `internal/updatehttp`. Release files must be immutable while served; cache identity is path, size, and mtime, with context fixed per handler. The source preserves manifest hash/size when download headers differ, including on fallback. Manifest digest fields are fixed policy, not aliases: `UpdateInfo.Digest` is the release hash and `sha256` means SHA-256 only — a `NewHash` configuration (an explicit `sha256.New` included) rejects any nonempty `sha256` field regardless of its value, and without `NewHash` both fields must be valid SHA-256 hex that agree when both are present.
- Update hooks: `AcceptVersion` precedes retry gating and never charges a rejection; each rejected version warns once per resident lifetime. `PreRestartFunc` follows selftest/version probing and precedes both apply paths and staged approval. Cancellation cleans up without a refusal or retry charge.
- Log mirrors: nonblocking writers and supervision writers are process-lived. Initialize supervision logging once in watchdog run mode. Rotation stays in an untagged file for host-independent tests; the Windows selector shares `process.IsWindowsService` with SCM startup.

- Consumer contracts: liveness files contain only a decimal UnixNano deadline; dumps use `goroutine-dump-<unix seconds>.txt`. `ResidentWatchdogStale` must return false for an empty resident version. Update retry state is one in-memory failing-version record, gates only after an offer, and never counts cancellation or a watchdog restart request.

- Core dependencies are procguard and the Go standard library; Prometheus stays in the optional metrics package.
- Use table-driven tests
- `pkg/daemonpilot` cannot import `internal/updater` or `internal/watchdog` (circular dependency); factory functions use package-level variables swapped in tests
- Capability checking: `SupportsEnable()`, `SupportsStart()`, `SupportsStatus()`, `SupportsScope(scope)` on ServiceManager; CLI handlers check these before calling operations. Extends the existing `CanRestartWatchdog()` pattern. Every manager returns true for `daemon.ScopeSystem`; systemd, launchd and crontab return true for `daemon.ScopeUser` (launchd via a LaunchAgent under `~/Library/LaunchAgents` bootstrapped into `gui/<uid>`, crontab because it always edited the invoking user's crontab), the other eight return false, and `daemon.DetectForScope` filters on it. Optional capabilities stay off the interface and are reached by type assertion, as `EnvironmentFileReadWriter` already is — `LingerChecker`, `RegistrationVerifier`, `DomainReporter` and `ConfigRollbackWriter` follow that pattern. `ConfigRollbackWriter.WriteConfigForRollback` is the write a caller uses when it is itself rolling back: `WriteConfig` restores — and, for launchd, reloads — the manifest it overwrote when the init system refuses the new one, which is exactly wrong there, since what is on disk is the manifest being rolled back away from. Every `pkg/daemonpilot` rollback path goes through `writeConfigForRollback`, never `mgr.WriteConfig`
- BusyBox/sysvinit flag file fallback: on systems without K/S prefix support, enable/disable uses `/etc/init.d/<name>.disabled` flag files instead of renaming init scripts
- Init-system command errors: never wrap the error from `commandExecutor.Run` directly — the discarded `CombinedOutput()` is the only thing that explains _why_ a `systemctl`/`launchctl`/`rc-update` call failed. Use `runErr(action, out, err)` in `internal/daemon/manager.go`; it appends the trimmed output (truncated to 512 bytes) and keeps the original error unwrappable. The `action` prefix belongs to `runErr` alone — a `pkg/daemonpilot` handler adds the service name and nothing else (`fmt.Errorf("%s: %w", cfg.Name, err)`), because adding a verb too produces `starting service: starting service: exit status 113`
- Manager initialization: bind a detected manager with `daemon.InitServiceManagerWithOptions(mgr, daemon.ManagerOptions{...})`. Do not add a `SetX`-style setter that type-switches on one manager and silently no-ops for the other ten; add a field to `ManagerOptions` instead. `InitServiceManager(mgr, name)` remains as a thin name-only wrapper, used by tests. In `pkg/daemonpilot`, `install` and `run` detect — through `prepareManager(opts)` / `daemon.DetectForScope`, never `daemon.DetectServiceManager` directly, so an unsupported scope fails instead of silently installing machine-wide — and every post-install handler goes through `prepareInstalledManager`/`managerForState`, which rebuild the manager from `StateData.InitSystem` via `daemon.NewServiceManagerByName` and refuse on scope divergence. Do not add a fresh detection call to a lifecycle handler; anything that must know the _host_ init system (drift checks, the embedded log filter) reads `Detection.HostInitSystem`, never `mgr.Name()` of a manager built from state
- Install scopes: scope comes only from `Config.Scope` — no CLI flag, no `DAEMONPILOT_SCOPE`, no euid-based resolution, no `ScopeAuto`. User-scope artifact paths derive from `$HOME` alone; `XDG_*` is legal only as a detection predicate (`userManagerReachable`) and as child-process environment for `systemctl --user`, never to place files. `SetDefaults()` returns `error` and rejects user scope with an unresolvable `$HOME`. System scope must stay byte-identical in both manifests and state files, which is why every new `StateData` field carries `omitempty` and is written only for user scope — the deliberate exceptions are the launchd log path, moved off world-writable `/tmp` to `/var/log/<name>/`, so existing macOS installs report configuration drift until they are reinstalled or `update-config`ed, and `StateData.RollbackDigest`, written in both scopes because the staged-update rollback path exists in both; it is transient (recorded when the `.rollback` copy is created, cleared when it is consumed) rather than install-identifying. Because `RecordRollbackDigest` creates a state file for a service that was never installed through daemonpilot, a state file no longer implies an install: `StateData.recordsAnInstall()` (`InitSystem != ""`) gates both `loadInstalledState` and `readableState`, so a digest-only file reads as absent rather than sending `update-config` at an empty `ManifestPath`
- Launchd domains: the per-user domain is resolved once at install (`gui/<uid>`, falling back to `user/<uid>`), recorded in `StateData.LaunchdDomain` and restored through `ManagerOptions.LaunchdDomain`. Never re-resolve it in a lifecycle handler — a session with different login state would address a domain the agent was never bootstrapped into and orphan it. `uninstall` is the exception in the other direction: an unresolvable domain there does not abort, because refusing would leave a LaunchAgent with no supported way to remove it — it warns, calls `bootoutStaleDomains` so both per-user domains are still tried, and removes the plist. `Uninstall` runs `bootoutStaleDomains` even when the domain _does_ resolve, for the same reason `Install` does: `handleUninstall` also reads state through `readableState`, so a lost pin means the resolved domain may not be the one the agent was bootstrapped into, and removing the plist would leave a loaded job with nothing on disk able to unload it. `install` is the other exception: it detects rather than binds state, so it resolves its own domain, but `handleInstall` passes the previously recorded one as `ManagerOptions.PreviousLaunchdDomain` and `launchdManager.Install` boots that target out too — re-installing over SSH after a GUI install otherwise leaves the `gui/<uid>` job loaded against the same binary, with the state file now naming only `user/<uid>`. That record is not trusted as the only source: `bootoutStaleDomains` boots out _both_ `gui/<uid>` and `user/<uid>` in user scope, because `handleInstall` reads the previous domain through `readableState` — which reports an unreadable or corrupt state file as "no previous install" — and an install that failed before writing state never recorded a domain at all. Since `install` writes the pin every later command binds to, a state file that cannot be written now fails the install instead of warning: without it `start`/`stop`/`status` fall back to detection and may address a different init system or an empty launchd domain. The manifest is deliberately left in place, since `uninstall` works without a state file. A failed `bootstrap` that rolls the previous plist back also re-bootstraps it (`reloadRolledBackPlist`); the idempotency `bootout` already unloaded it, so without that a transient failure leaves a working service unloaded and unreachable. Status parses `launchctl print`, which nests sub-dictionaries carrying a `state` key of their own — read only the job dictionary's own keys
- Log directories: `Config.LogDir` flows through `buildServiceConfig` into `ServiceConfig.LogDir` and through `ManagerOptions.LogDir` into managers rebuilt from state. launchd and cron both refuse to create the parent of their log target, so every path that writes a manifest creates it — `Install` _and_ `WriteConfig`, since the `ConfigPatchers` install path and `update-config` never call `Install`. The log directory is created _before_ the manifest is written, not after: launchd auto-loads every plist under `~/Library/LaunchAgents` at the next login, so a plist left behind by an install that then failed on its log directory comes back on its own and fails to spawn, with no state file recording it. A crontab log directory may not contain `\n`, `\r` or `%`: cron splits on newlines and rewrites `%` into one before any shell quoting applies. The same three characters are refused for every other value that reaches a crontab command field — `ExecPath`, `WorkingDir`, each argument and each environment _value_ (`validateCrontabCommandFields`, alongside the existing `validateEnvKeys`; the rejection names the variable but never prints its value, since that is where tokens live and a percent-encoded secret is exactly what trips the check) — since quoting is applied long after cron has split the file: a newline there installs a second live line that `ParseCrontabEntries`, which removes the marker plus exactly one line, can never find again. All of it is hoisted ahead of the binary copy, because the manager-level check runs from `Install`, after the copy — the failed install writes no state file, so `uninstall` then reports the service as not installed and the copy is orphaned. `Config.validateCrontabFields` checks `LogDir`, `InstallDir` (which stands in for the `ExecPath`/`WorkingDir` the manager checks, since both derive from it and `Name` is already restricted to `[a-z0-9_-]`), every `ServiceArguments` entry, every `ServiceEnvironment` _value_, every `ServiceEnvironment` _key_ (through `daemon.ValidateEnvKeys`) and — through `daemon.ValidateCrontabSchedule` — `CrontabSchedule`, the one field of the entry that is not a command field but orphans the copy just the same. Add any new `Config` field that reaches a crontab line there, not only to the manager. It is called from `handleInstall` once `mgr.Name() == "crontab"`, between `prepareManager` and `copyBinaryToInstallDir` — **not** from `Config.Validate`: `%` is a cron hazard alone, and `Validate` runs from `New` at every process start, so refusing it unconditionally would stop an existing systemd or launchd service whose environment carries a percent-encoded value from booting at all. `Config.Validate` does refuse a relative `Config.LogDir`, which is init-system-independent. A system-scope launchd job carrying `UserName` also needs its log directory _chowned_ to that account: launchd opens `StandardOutPath` after dropping privileges, while root created `/var/log/<name>`. This was invisible while the target was world-writable `/tmp`. That chown is not unconditional: `MkdirAll` succeeds silently on an existing directory, so `ensureLogDir` chowns only a directory this call created (`fileSystem.DirExists` before `MkdirAll`) or the per-service default `/var/log/<name>`, which belongs to the service by construction — otherwise a `Config.LogDir` of `/var/log` would hand a root-owned system directory to an unprivileged service account. `fileSystem.Chown` is `os.Lchown`, not `os.Chown`, for the same reason: it runs as root, so following a symlink an unprivileged account pre-created under a writable parent would hand over whatever it points at
- Launchd plist rollback: `launchdManager.Install` reads the plist it is about to overwrite (`readPlistFile`) and, when `launchctl bootstrap` fails, calls `rollbackPlist` — restoring what it overwrote and deleting only a plist this install created, the same asymmetry the crontab manifest rollback uses. Deleting unconditionally would turn the documented asynchronous-`bootout` race (`Bootstrap failed: 5: Input/output error`) into the destruction of a working install whose state file still points at the plist. A read error that is not `fs.ErrNotExist` aborts before anything is mutated rather than being read as absence. `WriteConfig` does exactly the same, for the same reason `crontabManager.WriteConfig` does — it is the install path whenever `ConfigPatchers` is set, so its first-install case has no state file either, and a plist left behind there is auto-loaded at the next login with nothing recording it. `WriteConfig` also boots out `PreviousLaunchdDomain`, which only `Install` used to. The plist a rollback restores is re-bootstrapped into `rollbackDomain(resolved)` — `m.previousDomain` when set, since that is the domain the untouched state file still records; reloading into the newly resolved domain after a failed cross-session re-install would leave the job in `user/<uid>` while state says `gui/<uid>`, and every later `start`/`stop`/`status` would address an empty domain
- Crontab manifest ordering: both `Install` and `WriteConfig` write the `.daemonpilot-crontab-<name>.entry` manifest _before_ replacing the crontab, and on a failed `crontab <file>` restore whatever manifest they overwrote (deleting it only when there was none) — a manifest write that failed afterwards would leave a live entry with nothing to roll back from. `WriteConfig` needs this as much as `Install` does: it is the install path whenever `ConfigPatchers` is set, as well as the `update-config` write path. Every removal goes through `removeManifestFile`, which short-circuits on an empty `installDir` exactly as `readManifestFile`/`writeManifestFile` do — `manifestFilePath` returns a bare relative name there, so an unguarded `os.Remove` deletes a dot-file from the CLI's working directory
- Detection logging: `internal/daemon` logs through a package-level `DetectionLogger`. `NewDetectionLogger` gates the _debug trace_ on `LOG_LEVEL=trace|debug` but keeps warnings enabled at every other level, because `logDetectionWarn` carries outcomes that change what the install did — the fallback detector winning, a launchd domain that cannot be resolved, a manager selected only after the host's own init system was skipped for scope. Do not route those through `Debug`, and do not reintroduce a no-op logger for non-debug levels. The pre-`InitDetectionLogging` default stays a no-op so the package never writes to a caller's stderr uninvited. Operator advice that belongs to a `pkg/daemonpilot` handler still goes through `cfg.Logger` — the `@reboot` caveat is emitted there and deliberately _not_ repeated by `crontabManager.Install`, since both channels reach the same terminal
- Install preflight: privilege is decided by _probing_, never by comparing a uid. `preflight.go`'s `geteuid` exists only to word an error message; whether a path is writable is answered by `probeDirWritable` (create and remove a file in the nearest existing ancestor) and whether the copy can run is answered by executing `watchdog-version` from its destination (`preflightExec`). A non-zero exit from that probe is _not_ fatal — the host program owns its argument parsing — only `EACCES` (a `noexec` mount) and `ENOEXEC` (wrong architecture, missing loader) are. There is no `sudo`/`pkexec` re-exec and no `setuid`. Ordering is load-bearing: `gateInstallBeforeCopy` runs crontab field validation → executable resolution → write preflight → cross-scope preflight, all while the install has mutated nothing; `preflightExec` runs after the copy but before the manifest; and every failure from the copy to the state-file write unwinds through the `failed` closure, which unregisters the service and removes the lock file and the binary _only_ when this install created them. The unregistration runs first, while the binary it names still exists, and only once `installWithPatchers` has _succeeded_: removing the copy and leaving the manifest is the worse half-state (launchd auto-loads the plist at the next login and spawns a path that is gone), but calling `Uninstall` after a _failed_ `Install` would remove the registration the manager just rolled back to, which belongs to the install being replaced. `preflightCrossScope` probes the opposite scope's manifest path through the manager itself so it cannot drift, and it deliberately misses rather than invents: crontab is exempt (both its scopes edit the same crontab) and the system→user direction reads this process's `$HOME`, which is root's under `sudo`
- Single-instance lock: the lock file is opened `O_NOFOLLOW|O_NONBLOCK` and refused when it is anything but a regular file — `O_NOFOLLOW` stops a symlink, but a FIFO opens cleanly, `flock` on one is not a lock (`EOPNOTSUPP` on Darwin), and a read-only open of one blocks forever, so both `openOwnedLockFile` and `chownFileNoFollow` open non-blocking and check `S_IFREG` on the descriptor before doing anything else. Root replaces a non-regular lock path (`replaceLockFile`) without the flock-before-unlink the ownership path needs, since no instance can be holding one; a non-root euid refuses. `removeInstanceLockArtifact` removes any non-regular file at the lock path without locking it, for the same reason it removes a symlink. A file owned by another account is refused outright, except as root, which unlinks and recreates it — a group-writable `/usr/local/bin` would otherwise let an unprivileged account permanently block a root daemon. _Because_ ownership is checked first, `handleRun` can make every lock error fatal: a lock nobody holds is not a lock. The corollary is that install must hand the file over in advance — `ensureServiceUserLockFile` creates `<name>.lock` and chowns it to `Config.ServiceUser` (`os.Lchown`, same reasoning as the launchd log directory), because the root-owned install directory would otherwise deny the unprivileged service account and turn a working install into a `Restart=always` crash loop. An existing lock file is re-chowned, never unlinked: unlinking detaches the inode a live instance holds. Two things bound the root replacement, because that chown makes a foreign-owned lock file the _normal_ case for a root invocation rather than an attack. It accepts `Config.ServiceUser`'s uid as an owner alongside the current euid (`acquireInstanceLock(lockPath, owner)`, fed by `serviceUserUID`) — recreating that file would leave a root-owned `0600` one the service account can never open again, which under a fatal lock error is exactly the crash loop the chown exists to prevent. And it `flock`s the file _before_ unlinking it, replacing only a lock nobody holds: unlinking detaches the inode the live instance is flocking, so the recreated file would lock cleanly and two supervisors would share one `InstallDir` — silently, which is worse than the `ErrAlreadyRunning` a holder now gets. `serviceUserUID` returns a `lockOwner`, and "no service account" and "an account `os/user` cannot resolve" are kept apart: a `CGO_ENABLED=0` build cannot see an NSS-provided account, so an unresolved owner _refuses_ the root replacement rather than performing it — the file is most likely the service account's own, and recreating it root-owned `0600` is the crash loop. For the same reason neither `ensureServiceUserLockFile` nor `chownStateFileToServiceUser` fails an install over an unresolvable account; they warn and leave the file to root, which is what every release before the chown existed did. The chown itself is `chownFileNoFollow`, not `os.Lchown`: a hard link is not a symlink, so it opens `O_NOFOLLOW`, `fstat`s, refuses anything that is not a regular file with `Nlink == 1`, and `fchown`s the descriptor it checked. `openOwnedLockFile` refuses `Nlink != 1` for the same reason ownership is checked: a hard link from one service's lock path onto another's is not a symlink either, and both would then `flock` one inode, so the second service reads a lock nobody took for it as `ErrAlreadyRunning` — under a fatal lock error, a permanent crash loop. A hard-linked file takes the ownership branch, not the non-regular one: another live instance may be holding that inode, so root `flock`s before unlinking. And a `flock` is only a lock while the file it was taken on is still the file at the path — `acquireInstanceLock` revalidates the locked inode's `dev`/`ino` against the path and retries, because a racer that opened the old inode before the root replacement flocked it can still lock the detached file afterwards. `removeInstanceLockArtifact` gates on `Lstat`, not `Stat`, and removes a non-regular lock path without locking it: a dangling symlink reads as absent to `Stat`, and leaving it wedges the next install against the symlink refusal with nothing able to clear it. `handleRun` also `MkdirAll`s `InstallDir` before locking, since nothing else on the run path creates it and the lock error is fatal
- Rollback integrity: a `.rollback` file's presence proves nothing — in user scope the watchdog, the worker and anything else running as that uid share the install directory. Every path that restores or reports one goes through `daemonpilot.VerifyRollbackBinary` against the digest `RecordRollbackDigest` recorded when the copy was made, never a bare `os.Stat`; a missing digest is unusable, not trusted by default. `fileDigest` uses `Lstat` and refuses non-regular files so a symlink cannot be hashed while the rename moves another file. Every path that consumes the copy calls `ClearRollbackDigest` (best effort — a stale digest only ever refuses a file, never accepts one). A digest that could not be _read_ is kept apart from one that did not match: `loadRecordedRollbackDigest` wraps `ErrRollbackDigestUnreadable`, never `ErrRollbackUnverified`, because the state file is rewritten in place (`writeFileNoFollow` truncates rather than renaming, so ownership survives the chown) and a start racing an `install`/`update-config` can observe it truncated — quarantining on that would destroy a valid copy over an unrelated command. The restore is refused either way; only the mismatch is destructive. A copy that fails verification is _quarantined_ (`QuarantineRollbackFile`, renamed to `.rollback.invalid`), not left in place: `stagedProbationPath` arms probation on presence alone, so a file that can never be restored would burn a full `RollbackTimeout` window and re-fire `OnCriticalFailure` at every start. Note the digest lives in the state file in the same directory, so this defeats substitution and stale artifacts, not an attacker who can already write that directory. Because the digest write is now on the staged-update path, the state file has to be writable by the account that runs the update: `chownStateFileToServiceUser` hands it to `Config.ServiceUser` at install for the same reason `ensureServiceUserLockFile` hands over the lock file. Without it `RecordRollbackDigest` fails `EACCES` on a root-owned `0600` file, `ApplyStagedUpdate` aborts and undoes its rename, and self-update is dead on every poll
- Per-init-system operator advice: lingering is a systemd concept, and `state.Lingering` is false for every manager that is not a `daemon.LingerChecker`. Anything that suggests a remedy (`lingeringNote`) must branch on `state.InitSystem`, or a macOS operator is told to run `loginctl`
- Cross-platform build tags: every `syscall` usage lives in a build-tagged file with a counterpart covering the platforms it excludes (for example `watchdog_unix.go`/`watchdog_windows.go` for leader-only diagnostics). Platform-specific process limits and their integer conversions belong to procguard. Tests must be host-independent: guard linux-only detection (`requireLinuxDetection`) and `RLIMIT_AS` tests (`requireLowerableAddressSpaceLimit`, `requireSettableRLimitAS`) instead of assuming a Linux runner
- Lock failure classification: lock acquisition has three outcomes: held (`LockStatusHeld` / `DAEMONPILOT_LOCK_STATUS=ok`), contention or a suspect path (fatal), and a measured lack of locking support (`ErrLockUnavailable`, `LockStatusUnlocked` / `DAEMONPILOT_LOCK_STATUS=unlocked`). A write-open failure caused by a read-only filesystem or an unwritable directory first retries the existing file `O_RDONLY`, because `flock` needs no write access and this preserves a genuine lock on a read-only mount; the descriptor still goes through every regular-file, ownership, link-count and post-flock inode check, and cannot repair a suspect object. Every other non-contention failure is classified by creating, flocking and removing a unique probe file in the same directory. A successful probe proves the original path itself is broken and keeps the failure fatal; only a failed probe proves no instance could establish the guarantee and permits a degraded run, which logs the path and both errors at error level and exports the status to the worker. Do not replace this capability measurement with errno enumeration or persisted state. The invariant is fail-closed for contention and suspect lock objects; only a host measured to be incapable of locking at all runs unlocked, and it says so. Root repairs a symlink through the same no-follow, `O_EXCL` replacement used for other non-regular objects
- Stopping the watchdog: `Shutdown()` and `stopRun()` are not interchangeable, and choosing the wrong one hangs the process rather than failing it. `Shutdown()` calls the worker supervisor's `Stop()` only — it stops the worker while the watchdog keeps running. `stopRun()` cancels the RUN context, which is the only thing `runHealthChecks` and `runProbation` select on, and therefore the only way `Run()`'s `wg.Wait()` can ever return. **Every path that needs `Run()` to RETURN — all three callers that set `needsExecRestart`, and anything ending the watchdog — must call `stopRun()`.** The staged-update branch called `Shutdown()` and hung forever on any host whose application supplies a `HealthFunc`: the worker was reaped, the exec never happened, and what was left was a live process holding the instance lock with no worker and no supervised children. A test for these paths must set `HealthFunc`, or it exercises the branch without the goroutine that makes it hang — which is exactly why the existing one passed
- Orphan prevention: worker processes detect parent (watchdog) death and self-terminate automatically
  - Linux: procguard configures kernel SIGTERM on parent death and watches the expected parent PID; daemonpilot retains signal handling and parent-exit warning fields
  - macOS/BSD: procguard watches the expected parent PID every 5 seconds and daemonpilot cancels application work on reparenting
  - Windows: procguard assigns workers and exec-through children to kill-on-close Job Objects; watchdog death or restart cleans up the assigned tree
  - Set `DAEMONPILOT_DISABLE_PARENT_MONITOR=1` to disable cooperative worker parent monitoring (testing only); procguard's parent-side process group/Job Object guarantees remain enabled
